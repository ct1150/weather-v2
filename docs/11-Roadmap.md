# Roadmap

> **Authoritative.** This document is the active source of truth for its domain; SPEC.md is the governance index.

## Release policy

This document is the sole owner of `first_release` and `lifecycle`. Every Active Hard requirement has exactly one deterministic release ID: `REL-${first_release}-${requirement_id.replaceAll("-", "_")}`. Domain documents store only that ID as `roadmap_ref` and link to its explicit anchor here.

Release order is **MVP → Beta → V1 → V2**. MVP contains every requirement except the explicitly approved delayed IDs represented below. Architecture, deployment, engineering, SEO, agent-delivery, analytics/privacy, and data-migration contracts have a Continuous lifecycle. Other feature contracts use Launch unless their acceptance criteria explicitly require ongoing operation.

MVP provides typed static configuration and emergency kill switches. Dynamic segmentation, rollout, and experimentation Feature Flags begin in V1. Lighthouse scores of 100 remain product targets; enforceable CI and production thresholds are owned by the engineering performance contract.

## Phase gates

Each delivery phase records a decision summary, verification evidence, known limitations, and the next step. A phase may advance only after its exact verification commands have run and the responsible reviewer has approved the evidence. A checkbox or existing file is not proof of completion.

Draft migration does not authorize product implementation. The complete staged set must pass parser, requirement, release, trace, link, and derived-coverage checks before the controlled cutover. Active release work then follows the order MVP, Beta, V1, and V2; later-release details are planned only when their release enters delivery.
